# Проверка общего кода трёх инструментов — 2026-09-06

## Дополнение после первого подключения

Ниже сохранён исходный аудит до реализации. После него в наших рабочих папках
GitNexus и CodeGraph добавлены продуктовые `agent/cli.mjs` / `agent/engine.mjs`,
которые непосредственно импортируют библиотеку и запускают собственные сборки.
Проверены настоящие внешние индексы двух веток, копирование закрытой базовой
версии, достроение, сохранность предыдущей версии при ошибке и перечитывание
настроек. Описание общих примитивов: [git-checkout](git-checkout.md).

58 проверок библиотеки прошли на Node.js 22.19.0; по три проверки продуктового
подключения GitNexus и CodeGraph также прошли. У GitNexus журнал подтверждает
изменение одной строки файлового индекса с сохранением двух неизменённых строк.
В CodeGraph найдено и исправлено сохранение прежнего имени ветки/коммита после
достроения: теперь они обновляются после успешной полной сверки файлов.

Живые обработчики, старые общие настройки и глобальные команды не переключены.
Graphify пока остаётся на исходной v8: настройка защитного правила на origin/v8
требует отдельного разрешения. Автоматической очистки и миграции старых мест нет.
Политика выбора нескольких баз пока консервативна: при неоднозначности строится
полный индекс с записанной причиной. Это не доказательство исторической родительской ветки.

Перед переходом на Node.js 26 пользователь потребовал отдельные коммиты текущей
работы. Переход не реализован: GitNexus допускает 26 по package.json; CodeGraph
ограничивает версии ниже 25 и имеет явную проверку при запуске. Однократная
проверка GitNexus на установленной 26.3.0 прошла до требования остановить эксперименты;
сохранённое состояние проверяется на 22.19.0.

## Краткий результат

Прямого подключения `ai-agents-library` в проверенных исходниках и зависимостях
GitNexus и CodeGraph нет. В Graphify нашей отдельной ветки ещё нет; библиотека
также не подключена. Наличие общей библиотеки, записанного плана или поля с
путём исходников не является доказательством работающего подключения.

Готовы модули расположения данных проекта и нового выбора веток `branch-targets`.
Не завершены продуктовые подключения, перенос живых настроек, общая защита
индексов от удаления и наследование базового индекса. Не добавляем вместо них
новый диспетчер в AI-POOL.

Проверка адресная: ветки, импорты, зависимость, размещение данных, сведения о Git
и существующие места запуска. Это не полный аудит безопасности всех исходников
и не испытание скорости настоящих индексаторов.

### GitNexus

- [getStoragePath](../../.worktrees/gitnexus-codex-branch-indexes/gitnexus/src/storage/repo-meta.ts)
  пока возвращает `.gitnexus` внутри переданного проекта. Требуется адаптер
  собственных внешних путей, а не запись настроек в анализируемый проект.
- [resolveBranchPlacement и branchSlug](../../.worktrees/gitnexus-codex-branch-indexes/gitnexus/src/storage/branch-index.ts)
  уже различают размещение явных веточных индексов. Это существующая возможность
  продукта, не общий выбор списка targets и не копирование базового графа.
- [storage/git.ts](../../.worktrees/gitnexus-codex-branch-indexes/gitnexus/src/storage/git.ts)
  имеет определение общей папки репозитория и текущей ветки. Общую идентичность
  конфигурации можно получать из библиотеки, но фактическую рабочую папку нельзя
  заменить основной при чтении исходников.
- Наши сохранённые изменения: проверка устаревания с учётом ветки и удаление
  установочной статистики Scarf. Незакоммиченные изменения установки навыков
  нельзя терять при подключении библиотеки.

### CodeGraph

- [getCodeGraphDir](../../codegraph-privacy/src/directory.ts) строит `.codegraph`
  внутри проекта. `CODEGRAPH_DIR` допускает только имя подпапки, не внешний путь:
  одной переменной окружения для нового расположения недостаточно.
- Наша [detectGitIndexInfo](../../codegraph-privacy/src/git-metadata.ts) принимает
  `CODEGRAPH_INDEX_BRANCH` и сохраняет ветку/номер снимка. Это можно связать с
  результатом общего выбора целей, но сама функция не выбирает несколько веток.
- [sync/worktree.ts](../../codegraph-privacy/src/sync/worktree.ts) обнаруживает
  использование индекса чужой рабочей папки. Сохранить эту проверку при изменении
  путей; единая идентичность проекта не делает содержимое разных веток одинаковым.
- [project-config.ts](../../codegraph-privacy/src/project-config.ts) читает
  проектный codegraph.json и сохраняет результат по времени изменения файла.
  Наши личные настройки вынести во внешний конфиг, не уничтожая существующие
  добровольно созданные проектные настройки и не перенося их смысл в библиотеку.
- Запрет отправки статистики в [telemetry/index.ts](../../codegraph-privacy/src/telemetry/index.ts)
  остаётся в нашей ветке продукта. Не заменять запрет общим флагом, который можно
  нечаянно включить.

### Graphify

- [paths.py](../../graphify/graphify/paths.py) уже допускает абсолютный GRAPHIFY_OUT,
  но значение фиксируется при загрузке модуля. Для новых настроек без перезапуска
  нужен продуктовый способ получать выбранные пути на каждом действии.
- Движок написан на Python. Будущая наша ветка может иметь небольшой запускатель
  на Node.js, который вызывает библиотеку и передаёт результат движку как
  структурированные данные. Общие правила не копировать второй раз на Python.
  Сам такой запускатель ещё не написан и не установлен.
- [watch.py](../../graphify/graphify/watch.py) и [cache.py](../../graphify/graphify/cache.py)
  уже умеют обновлять граф и повторно использовать результаты по файлам. Это не
  подтверждение поддержки продуктового targets или клонирования индекса базовой ветки.
- В [HTML-выгрузке](../../graphify/graphify/exporters/html.py) остаётся внешний
  исполняемый файл с unpkg.com. Для автономного приватного представления нужен
  локальный файл. Само наличие ссылки не доказывает отправку графа наружу.

## Что имеет смысл обобщить следующим

1. **Сведения о Git для выбора целей.** Одинаковый контракт наблюдения: фактическая
   рабочая папка, общий проект, имя выбранной ветки, номер снимка, удалённые
   источники. Собирать ограниченными командами без автоматического получения
   изменений и без догадок при ошибке. Пока resolver принимает данные от продукта.
2. **Безопасная папка ветки по полному идентификатору.** Старый branchStorageName
   превращает feature/x и feature-x в одно имя. В GitNexus уже есть собственное
   устранение совпадений. Нужен общий договор размещения с сохранением старых
   связей, а не слепая замена имён существующих каталогов. Новый branchKey эти
   ветки различает, но сам не является именем каталога.
3. **Решение о сохранении индекса.** Входами должны быть разрешённые targets,
   активные рабочие папки, используемые и последние готовые версии индекса.
   Не заводить второй независимый список всегда индексируемых веток вместо
   уже существующего targets. Общее решение не удаляет файлы; действие продукта
   возможно только при отдельном разрешении и повторной проверке под блокировкой.
4. **Проверка совместимости базовой копии.** Общие правила по версии инструмента,
   формату индекса, настройкам и действительно индексированному снимку можно
   разделить. Выбор неоднозначной базы, согласованное копирование базы и её
   достраивание остаются в каждом движке.
5. **Запись происхождения сборки и обновления.** Единые поля старой/новой основы,
   сохранённой версии, наших изменений и результатов испытаний пригодны всем
   трём. Библиотека не должна сама фиксировать рабочие изменения или переносить ветку.
6. **Формат сравнительного испытания.** Одна схема времени, стоимости, качества
   и конфигурации для работы с каждым инструментом и без него; сами измерения
   проводить отдельно, не выводить выигрыш из наличия графа.

Это кандидаты для общей реализации, а не список уже перенесённых модулей.
В частности, `writeJsonAtomic` и блокировка в project-locations пока внутренние
функции: их нельзя обещать как готовый публичный механизм записи любых баз.

## Порядок безопасного подключения

1. Подготовить и проверить общий модуль — выполнено для branch-targets.
2. Завершить разрешённое обновление наших исходников; отдельно согласовать
   правило создания нашей ветки Graphify и сохранение незавершённых изменений GitNexus.
3. Подключить библиотеку в наших продуктовых ветках, не в AI-POOL или корпоративных проектах.
4. Проверить каждую настоящую сборку: выбранная ветка, заданная другая ветка,
   повторное чтение настроек и отсутствие записи в исходный проект.
5. Только затем явно преобразовать живые настройки и заменить старые места запуска.
   Старые индексы и файлы не удалять автоматически.

Живой файл `~/.agents/skills/git-nexus/config/projects.json` по-прежнему обслуживает
старую интеграцию сразу двух инструментов. Это обнаруженное прежнее состояние,
а не новая целевая архитектура. Его current сейчас нельзя просто заменить
строкой __CURERNT__ до переключения обработчика.
